# 부동산 경·공매 서비스 데이터 통합 ETL 플랫폼 구축
- 다양한 공공기관 데이터를 통합하여 Property Master(경·공매 부동산 마스터 데이터)를 구축한 ETL 플랫폼
  
## 기간 : 2023.10 ~ 현재

## 역할 
- ETL 설계
- Airflow DAG 개발
- 데이터 모델 설계
- 데이터 통합
- 운영 및 장애 대응

## 사용 기술
- Python
- Airflow
- MSSQL
- Pandas
- Pydantic
- AsyncIO
- REST API
- Docker

# 프로젝트 배경
- 부동산 경매·공매 서비스는 하나의 물건 정보를 제공하기 위해 여러 공공기관의 데이터를 한 곳에서 봐야합니다.
- 예를 들어 사용자가 하나의 경매 물건을 조회하면 다음과 같은 정보를 함께 확인합니다.
- 경매 정보, 공매 정보, 건축물 정보, 실거래가, 토지이용계획, 등기부등본, 학군정보 등
- 그러나 각 기관은 데이터 제공 방식과 식별자가 서로 달라 단순한 데이터 조회만으로는 하나의 물건 정보를 구성할 수 없었습니다.
- 따라서 여러 기관의 데이터를 공통 식별자를 기준으로 연결하고, 하나의 Property Master 데이터셋으로 통합하는 ETL 플랫폼이 필요했습니다.

# 프로젝트 목표
- 다양한 기관 데이터를 자동 수집
- 주소 및 식별자 정규화
- Property Master 구축(경·공매 부동산 마스터 데이터)
- 증분 ETL 자동화
- 서비스 및 Data Mart에서 공통 활용 가능한 데이터 ETL

# 전체 아키텍처

# 데이터 통합 설계
- 데이터 특성에 따른 다중 식별자 매핑
- 대법원 경매 물건을 기준으로 여러 공공기관 데이터를 연결했습니다.
- 기관별로 관리 단위와 식별체계가 달라 하나의 공통키를 강제로 적용하지 않고, 데이터 특성에 따라 서로 다른 식별자를 사용했습니다.
```
                  경매 물건
             사건 식별자 + 물건번호
                       │
       ┌───────────────┼───────────────┐
       ▼               ▼               ▼
   소재지코드     부동산고유번호     자체 건물코드
       │               │               │
       ├ 건축물대장     └ 등기부등본    ├ 단지정보
       ├ 토지이용계획                   └ 실거래가
       └ 위치·학군정보
```
## 주요 통합 기준
- 데이터 영역 통합 기준
- 경매 물건 사건 식별자 
- 주소·토지 소재지코드
- 건축물 상세 소재지코드 + 동·층·호
- 등기 정보 부동산고유번호
- 단지·실거래 자체 표준화 코드
  
## 설계 포인트
- 주소 표기 차이와 기관별 식별체계의 불일치를 해결하기 위해 주소 정규화와 단계별 매핑을 적용했습니다. 
- 매핑 실패 데이터는 별도로 분리하여 재처리하고, 아파트·오피스텔·빌라는 자체 표준화 코드를 생성해 실거래 및 단지정보와 연결했습니다.
- DB에 전국 법정동/행정동 코드를 넣어놓았고 DB 우선 매핑 후 외부 주소 API 재검색, 실패 데이터 정규화 및 재처리 구조로 운영했습니다.

                           │
                           ▼

                   Normalize

## ETL Pipeline
### Extract
- 기관별 데이터 자동 수집
- 증분 수집 기반 ETL 수행
### Validate
- 필수 데이터 검증
- 중복 및 스키마 검증
### Normalize
- 주소 및 코드 표준화
- 데이터 형식 통일
### Match
- 기관별 식별자 매핑
- 통합 데이터 생성
### Transform
- 비즈니스 규칙 적용
- 서비스용 데이터 생성
### Load
-Raw → Refined → Service → Data Mart 적재
### Retry
- 실패 데이터를 Error Table에 저장
- 재처리를 통해 데이터 유실 최소화
  
# 주소 정규화 및 매핑 전략

## 기관별로 다른 주소 데이터를 하나의 기준 데이터로 통합

### 문제

공공기관마다 동일한 부동산를 서로 다른 형식의 주소로 관리하고 있었습니다.

* 행정구역 표기 차이
* 도로명·지번 주소 혼용
* 공백 및 특수문자 차이
* 기관별 주소 포맷 불일치
* 비정상적으로 제공되는 주소 데이터

이러한 문제로 단순 문자열 비교만으로는 동일한 부동산을 정확하게 매핑할 수 없었습니다.

---

## 주소 정규화 프로세스

```text
                기관별 주소 수집
                      │
                      ▼
              기존 주소 DB 매핑
                      │
          ┌───────────┴───────────┐
          │                       │
      매핑 성공               매핑 실패
          │                       │
          ▼                       ▼
   소재지코드 사용          카카오 주소 API
                                  │
                     ┌────────────┴────────────┐
                     │                         │
                 검색 성공                 검색 실패
                     │                         │
                     ▼                         ▼
              소재지코드 생성          주소 정규화
                                               │
                          ┌────────────────────┼────────────────────┐
                          │                    │                    │
                    공백 제거          주소 형식 보정         행정구역 표준화
                                               │
                                               ▼
                                      카카오 API 재검색
                                               │
                                               ▼
                                        소재지코드 생성
```

---

## 핵심 설계

### ① 기존 주소 DB 우선 매핑

이미 수집되어 있는 주소 정보를 우선 활용하여 불필요한 API 호출을 최소화했습니다.

**효과**

* API 호출량 감소
* 처리 속도 향상
* 중복 검색 방지

---

### ② 주소 API 기반 표준화

DB에서 찾지 못한 주소는 카카오 주소 API를 이용하여 표준 주소와 소재지코드를 생성했습니다.

이를 통해 기관마다 다른 주소 표현을 하나의 기준 주소로 통일했습니다.

---

### ③ 실패 데이터 재처리

API 검색에 실패한 주소는 즉시 제외하지 않았습니다.

별도의 실패 대상으로 분리한 후 다음과 같은 정규화 규칙을 적용하여 재검색했습니다.

* 불필요한 공백 제거
* 특수문자 제거
* 행정구역 표기 통일
* 주소 형식 보정
* 문자열 예외 처리

정규화 이후 다시 주소 API를 호출하여 대부분의 주소를 자동으로 복구했습니다.

---

## 최종 매핑 기준

주소 문자열 자체를 연결키로 사용하지 않고, 생성된 **소재지코드**를 기준으로 데이터를 통합했습니다.

```text
기관별 주소
      │
      ▼
주소 정규화
      │
      ▼
소재지코드 생성
      │
      ▼
건축물대장
토지이용계획
실거래가
학교정보
위치정보
```

## 성과
* 주소 형식이 서로 다른 기관 데이터를 동일한 기준으로 통합
* 주소 검색 실패 데이터를 정규화하여 자동 복구
* 소재지코드 기반의 일관된 데이터 연결 체계 구축
* 데이터 품질 향상 및 매핑 정확도 개선

## 핵심 설계
- 기관별로 서로 다른 주소 문자열을 직접 비교하지 않고, 주소를 표준화하여 소재지코드라는 공통 식별자를 생성함으로써 여러 공공기관 데이터를 안정적으로 통합했습니다.
- 주소를 Primary Key로 사용하지 않은 이유
```
- 기관마다 주소 표현 방식이 다름
- 주소 변경 가능성 존재
- 동일 주소의 다양한 표기 존재
↓
공통 식별자인 소재지코드를 생성하여
데이터 통합 기준으로 사용
```

# 트러블 슈팅
## 1. 증분 수집 전략 (Incremental ETL)
### 문제
- 전체 데이터를 매번 다시 수집할 경우 다음과 같은 문제가 발생할 수 있었습니다.
  - 불필요한 API 호출
  - 수집 시간 증가
  - 기관 서버 부하 증가
  - 동일 데이터 반복 처리
### 설계
```
  Airflow Scheduler
        │
        ▼
마지막 수집 시각 조회
        │
        ▼
변경된 데이터만 조회
        │
        ▼
ETL 수행
        │
        ▼
수집 완료 시간 저장
```

### 핵심 전략
- 변경 데이터만 조회
- 이미 처리된 데이터 제외
- 수집 완료 시점 관리
- 실패 시 마지막 성공 지점부터 재수집

### 기대 효과
- 처리 시간 단축
- 중복 처리 최소화
- API 호출 감소

## 2. 공공기관 IP 차단
### 문제
- 동일 기관에 반복적으로 요청하면 IP 차단 또는 응답 실패가 발생했습니다.
  
### 원인
```
다량 요청(수집)
  ↓
기관 Rate Limit
  ↓
IP 차단
```

### 해결
```
요청 간격 조절
  ↓
Retry
  ↓
실패 데이터 분리
  ↓
다음 ETL 재수집
```

### 설계 포인트
- 요청 속도 제한
- Retry 적용
- 실패 데이터 별도 관리
- 다음 배치에서 자동 복구
  
### 결과
- 단순 실패로 처리하지 않고 운영 중 자연스럽게 복구 가능한 구조를 설계했습니다.

## 3. DB 병목현상 개선
### 문제
- 초기 ETL은 데이터를 한 건씩 INSERT/UPDATE 하는 방식으로 처리했습니다.
- 데이터가 많아질수록 DB I/O가 증가했고, ETL 수행 시간이 길어지는 문제가 발생했습니다.
- 
### 문제에 대한 결과
- DB 연결 횟수 증가
- Transaction 오버헤드 증가
- ETL 처리시간 증가
- DB 부하 증가

### 해결
- 데이터를 메모리에 모은 후 Batch Upsert(MERGE) 방식으로 변경했습니다.
```
 ETL
  ↓
Batch 생성
  ↓
MERGE
  ↓
INSERT/UPDATE/동시 처리
```

### 설계 이유
- 단순 Batch Insert가 아니라 Upsert(MERGE) 를 선택한 이유는, 신규 데이터는 INSERT, 기존 데이터는 UPDATE를 하나의 SQL에서 처리할 수 있기 때문입니다.
- 증분 ETL 환경에서는 이미 존재하는 데이터와 신규 데이터가 함께 들어오기 때문에 Upsert 방식이 적합했습니다.

### 결과
- DB 호출 횟수 감소
- Transaction 횟수 감소
- ETL 처리시간 개선
- 대량 데이터 처리 안정성 향상
- 
### 핵심 
- 한 건씩 처리하던 방식을 여러 건을 한 번에 처리하는 Batch Upsert 방식으로 변경하여 DB 병목을 개선했습니다.

# 성과 및 회고
## 성과
- 여러 공공기관 데이터를 하나의 ETL 파이프라인으로 자동화
- 주소 표준화를 통해 데이터 연결 품질 향상
- 증분 수집을 적용하여 불필요한 처리 감소
- 운영 중 발생하는 실패 데이터를 재처리할 수 있는 구조 설계
  
## 회고
- 이번 프로젝트를 통해 가장 크게 배운 점은 데이터를 수집하는 것보다, 서로 다른 데이터를 신뢰성 있게 연결하는 것이 더 어렵다는 것이었습니다.
- 공공기관마다 주소 체계와 식별자가 달라 단순한 수집만으로는 서비스를 만들 수 없었으며, 주소 표준화와 식별자 매핑이 데이터 품질을 결정하는 핵심 요소였습니다.
- 또한 ETL은 데이터를 적재하는 것으로 끝나는 것이 아니라, 장애 발생 시 복구 전략과 증분 수집, 데이터 품질 관리까지 고려해야 안정적으로 운영할 수 있다는 점을 경험했습니다.
- 앞으로는 Spark 기반 대용량 처리와 CDC 기반 실시간 데이터 파이프라인까지 확장하여 더 안정적인 데이터 플랫폼을 구축해보고자 합니다.

# 현재 포폴의 문제점

## 1. 정량 지표가 거의 없습니다.
"처리 시간 감소", "API 호출량 감소", "DB 부하 개선" — 전부 방향만 있고 숫자가 없습니다. "몇 시간에서 몇 시간으로 줄었는지", "API 호출 몇 % 감소했는지", "매칭 성공률이 몇 %인지"가 하나도 없어요. 10년차 이상이면 이걸 제일 먼저 물어봅니다. "그래서 몇 % 개선됐어요?"라는 질문에 숫자로 답 못하면 신뢰도가 확 떨어집니다.

## 2. 규모가 사실 크지 않은데 스택이 무겁습니다.
일 60~65만 건은 MSSQL 하나로도 충분히 커버 가능한 규모입니다. Airflow 30개 DAG, AsyncIO, Docker까지 쓸 정도로 "빅데이터"는 아니에요. 시니어라면 "이 규모에 왜 이렇게 복잡한 스택을 썼나, 오버엔지니어링 아닌가"를 물어볼 가능성이 높습니다. 스택 나열이 오히려 역효과가 날 수 있는 지점이라, "왜 이 규모에 이 아키텍처가 필요했는지"에 대한 답을 미리 준비해야 합니다.

## 3. AsyncIO가 어디 쓰였는지 불명확합니다.
Airflow 태스크는 기본적으로 동기 실행 모델인데 AsyncIO가 어느 계층(수집? API 병렬 호출?)에 쓰였는지 문서에 안 나와 있습니다. 이런 식으로 "기술 키워드는 나열했는데 어디서 왜 썼는지 연결이 안 되는" 부분은 면접에서 바로 걸립니다.

## 4. 테스트/데이터 품질 검증 얘기가 전혀 없습니다.
Pydantic으로 스키마 검증한다는 것 외에 유닛테스트, 데이터 품질 모니터링(매칭 성공률, 결측률 추적), 회귀 테스트에 대한 언급이 없습니다. 프로덕션 ETL을 "운영"까지 했다고 주장하는데 이 부분이 빠지면 "정말 운영 성숙도가 있었나?" 의심받습니다.

## 5. 도메인 리스크(경매 데이터 특성)를 안 건드렸습니다.
경·공매는 입찰 마감일이 있는 시간 민감 데이터입니다. "데이터가 며칠 지연되면 실제 서비스에 어떤 영향이 있는지, SLA/신선도 기준이 뭔지"가 전혀 없어요. 이건 도메인 이해도를 보여줄 수 있는 좋은 포인트인데 놓쳤습니다.

## 6. 등기부등본 같은 민감 데이터의 보안/컴플라이언스 언급 없음.
부동산·등기 데이터는 개인정보에 가까운데 접근 통제, 마스킹, 로그 관리에 대한 언급이 전혀 없습니다. 시니어급 리뷰에서는 "이거 개인정보 이슈 없어요?"라는 질문이 나올 수 있습니다.

## 7. 혼자 다 했다는 뉘앙스.
역할란에 "ETL 설계·Airflow DAG 개발·데이터 모델 설계·데이터 통합·운영 및 장애 대응"이 전부 본인 몫처럼 적혀 있는데, 팀 규모/본인 기여도 비중이 안 나와 있습니다. 이런 경우 "이거 혼자 다 하신 거예요?"라고 물었을 때 답변이 애매하면 신뢰도가 떨어집니다.

## 8. 회고의 "향후 방향"이 버즈워드 나열처럼 보입니다.
Spark, CDC, 데이터 리니지 — 다 맞는 방향이지만 "현재 어떤 구체적 페인포인트 때문에 이게 필요한지" 연결이 약합니다. 예를 들어 "현재 배치 처리 시간이 X시간이라 실시간성이 필요한 경우 CDC로" 같은 구체적 근거가 있어야 설득력이 생깁니다.
